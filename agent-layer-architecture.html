01

The system at a glance

The wallet UI, agent service, local model and execution service have separate responsibilities. Deterministic code owns every step, write and network call. The model supplies constrained interpretations.

Local inference, external reads

There is no remote model or Flex-hosted backend. Chain RPCs, the ENS indexer and user-shared URLs are still external services.

One model, separate contexts

“Dual LLM” means isolated privileged and quarantined calls to the same local model. No conversational memory is shared between them.

Intent planning only

The agent returns an answer, an error/refusal, or ordered intents. Signing keys and transaction execution remain in the wallet’s execution layer.

The model pairs known amount and recipient placeholders. Code checks that the pairing agrees with the instruction.

Input
Masked text and per-request schema enums containing only the permitted placeholders and supported fields.

Input
The validated plan and source mappings, plus notes about funding, address reuse and any relevant constraints.

03

Trust is explicit

The model can suggest an interpretation. Code validates it and preserves each value’s origin. Untrusted content cannot grant itself authority.

Privileged calls

S3 · S4 · S5 · S8
Allowed context

The user’s typed words, progressively masked. S3 sees the typed amount text; S8 pairs verified placeholders with code-built metadata.

Excluded authority

No tools, database access or network access. Raw pasted content, files and web pages never enter these prompts.

Quarantined call

S1 · per content item
Allowed context

One untrusted content item, a separate prompt and a typed extraction schema. Code tags every extracted candidate as untrusted.

Excluded authority

No user instruction, shared context, memory or tools. Extracted values require user confirmation and can never fund an autopay.

Deterministic code

The control plane
Owns

Parsing, checks, questions, placeholder mappings, chain reads, writes, schedules, bridge arithmetic and the allowed hand-off fields.

Must stop or ask

Missing or ambiguous transaction details. An uncovered state returns UNSUPPORTED_REQUEST and logs an unsupported_state event with a rule_id.

Execution layer

Separate service
Receives

A validated, confirmed envelope with concrete amounts, addresses, chains, dependencies and schedule data. Reports return through an authenticated API.

Never receives

Prompt text, story context, contact/ENS names, model placeholders or the UI summary. It has no direct access to the agent’s database.

01

Amounts stay exact

Decimal strings and bigint base units throughout. No floating-point arithmetic touches a monetary amount.

02

Logs carry metadata only

The allowlist logger restricts fields and their shapes. No amounts, addresses, names, prompt text or raw HTTP request logging.

03

Secrets are screened first

Typed input, pasted blocks, attachment text, answer text and supplied/redirect URLs are checked before their relevant persistence or processing paths.

04

Limits remain user-controlled

Persistent limits change only through the authenticated settings API. Eligible one-time consent cannot silently rewrite DB5.

Session close clears working context

DB1, DB3 and DB8 are cleared together. The database uses secure_delete and VACUUM. Persistent contacts, limits, spend records and autopays survive session close.

¹ The journal survives, its history does not

The confirmed envelope and delivery status remain for report correlation. Session history temporarily held by the journal is cleared when the session closes.

In-memory request: the current scan, model outputs, plan, question and step_state live in an AgentRequest. The durable journal records submissions; it is not a checkpoint for restarting an unfinished conversation.

Follow-up context: DB8 history supports follow-ups to handed-off payments. The current working tree also retains one narrowly eligible insufficient-funds payment in memory for an immediate amount correction (SQ-S-01). That correction gets a fresh request and confirmation; failed payments are not appended to DB8 history.

05

“Yes” is a boundary

Confirmation authorizes a specific resolved plan. Before its first submission, the agent checks that the assumptions still hold. An accepted hand-off and an executed payment are separate events.

RECEIVED→S0 … S10→AWAITING_CONFIRMATION→ yes →HANDED_OFF

  1. Pause, answer, resume

    A question keeps the request at its current step. The answer handler validates the reply; continue re-enters that step. Invalid answers have a bounded retry count. Only one call runs per session at a time.

  2. Refresh before the first submission

    Reload limits and refresh balances. Revalidate funding and spending. Changed settings trigger replanning; a changed summary requires another “yes”.

  3. Recheck time-sensitive autopays

    If the planned first occurrence has passed before any submission, ask for a new start, replan and confirm again. An ambiguous prior submission is retried with its original schedule.

  4. Restore values and persist identity

    swapBack resolves DB1 / DB3 placeholders, constructs an allowlisted envelope and validates its closed schema. Commit that envelope and DB6 / DB7 reservations before the outbound call.

  5. Submit, then reconcile reports

    POST the envelope with request_id as the idempotency key. The authenticated reports endpoint checks request, step, intent and autopay identity before updating the journal, spending or autopay state.

Agent → executor

POST /v1/intents

Authorization: Bearer …Dedicated outbound token from a local token file.
Idempotency-Key: request_idThe same key and envelope are reused on a retry.
Ordered, fully resolved intentsConcrete chains, token addresses, amounts, recipients, dependencies and applicable schedules.
Closed JSON schemaUnknown fields and unresolved values fail validation.

A retry preserves submission identity; the executor must honor the idempotency contract. The agent does not claim exactly-once blockchain execution.

2xx / valid callback

Accepted

Record acceptance and handed-off history. Execution results arrive separately. A later rejection cannot undo confirmed acceptance.

4xx / definite rejection

Rejected

Mark reservations failed and return EXECUTION_REJECTED. A confirmed execution callback takes precedence over a late rejection.

Timeout / 5xx

Delivery uncertain

Keep the reservations. A fresh user confirmation retries the same envelope, up to three attempts total. A local cancel after a timeout cannot recall a delivered request.

The four output intent types
ID Meaning Agent’s responsibility Executor’s responsibility
i One-time payment Resolve recipient, amount, token and chain. Sign and broadcast the transfer.
j Bridge for funding Calculate amount, padding and dependent payment steps. Execute the cross-chain transfer.
k Autopay Build schedule, caps, prefunding and job parameters. Set up and operate the recurring execution.
l Cancel autopay Identify the registered autopay to cancel. Cancel the scheduled execution.

A local request cancellation discards a pending plan. Cancelling an already active autopay is a separate l intent that follows the normal summary and confirmation path.

06

Small, explicit interfaces

Fastify binds to 127.0.0.1. The example configuration uses port 8787; Ollama uses 11434 and the executor uses 8788. Every API route requires authentication.

Method Route Purpose
POST /v1/sessions Open the single session with an IANA timezone; close the previous session.
DELETE /v1/sessions/:id Close the session and clear its working context.
POST /v1/sessions/:id/messages Start a request; route eligible conversational answers and confirmations.
POST /v1/sessions/:id/answers Answer the pending question.
POST /v1/sessions/:id/confirm Confirm or discard a summary; explicitly retry a failed hand-off.
POST /v1/sessions/:id/cancel Cancel the current eligible request.
GET / PUT /v1/settings/limits Read or update persistent agent limits. PUT is the sole DB5 settings-write path.
GET /v1/health Return database and local-model availability.
POST /v1/execution/reports Accept correlated intent results, autopay payments and autopay-status updates.
UI token

Authenticates session, message, answer, confirm, cancel, settings and health calls.

Report token

Authenticates executor callbacks. It must differ from the UI token.

Outbound token

Authenticates agent submissions to the configured execution service. Redirects are refused.

Valid agent-level outcomes use HTTP 200 with a structured response. Invalid HTTP input, authorization failures and state conflicts use HTTP errors. Reports return 204 on success. The request body limit is 20 MB.
